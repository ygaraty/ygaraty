## Question

Can Qwen3-Coder-30B-A3B-Instruct reuse our attention and expert kernels, execute
only its compiled tape, preserve numerical and tool-call correctness, and fit
useful contributor configurations? Measure memory and latency separately from
onboarding success. Related: [DO-48](DO-48.md) (Kolibri),
[DO-47](DO-47.md) (compiled-plan parity), [DO-52](DO-52.md) (Qwen hybrid geometry).

## Model and scope

Use the official [configuration](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct/blob/main/config.json)
and [model card](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct).
Pin their revisions and the quantized artifact before preparation.

| Property | Target |
|---|---|
| Architecture | `qwen3_moe`, 48 full-attention MoE layers |
| Hidden / query width | 2,048 / 4,096; these are different dimensions |
| Attention | 32 query heads, 4 KV heads, head dimension 128 |
| Experts | 128 per layer, top 8 per token, expert intermediate width 768 |
| Normalization / position | Per-head Q/K RMSNorm; epsilon 1e-6; full RoPE, theta 10,000,000 |
| Vocabulary | 151,936; untied input embedding and output projection |
| First experiment | Text, non-thinking, 4,096-token capacity, one conversation |

This is not the Qwen3.5 hybrid architecture. No DeltaNet/convolution state is
needed. The [upstream reference](https://github.com/huggingface/transformers/blob/v4.57.1/src/transformers/models/qwen3_moe/modeling_qwen3_moe.py)
uses float32 softmax routing, top-k selection and normalized selected weights.
It has no shared expert or Kolibri's router selection bias and post-branch norms.
Verify GGUF's Q/K layout and RoPE permutation against that reference; checkpoint
half-pair rotation cannot be copied blindly onto converted weights.

## Implementation map

Extend existing interfaces; do not create a parallel inference engine or copy
Kolibri's complete adapter. New family-specific code should describe weights,
configuration and the composition of reusable operations.

The source recipe must lower to these operations, with explicit buffer views
and sequence positions:

```text
h = rms_norm(x)
q, k, v = projections(h)
q, k = per_head_rms_norm(q), per_head_rms_norm(k)
q, k = rope(q, k, positions)
cache_store(k, v, sequence)
x = x + output_projection(causal_gqa(q, cache, sequence))
h = rms_norm(x)
ids, weights = normalized_top8(softmax(router_projection(h)))
experts = expert_down(silu(expert_gate(h, ids)) * expert_up(h, ids), ids)
x = x + weighted_expert_sum(experts, weights)
```

Embedding precedes the layer stack; final RMSNorm and vocabulary projection
follow it. Keep routing arithmetic and accumulation precision explicit. Do not
insert a shared expert, output gate, post-branch norm or hybrid attention state.
PyTorch may verify correctness on the authorized host; neither preparation nor
worker execution should require it.

## Capacity and placement

Start with contiguous whole-layer placement, keeping each layer's experts on
its owner. Do not introduce expert routing across machines for this experiment.
Initial split candidates are `[0,48]`, `[0,24,48]` and `[0,12,24,36,48]`; adjust
using actual packed bytes, endpoint overhead and measured execution cost.

Candidate fleets are 1 × 32 GiB, 2 × 16 GiB and 4 × 8 GiB GPUs. These are
screening targets, not admitted capacities. Active parameter count does not
reduce resident weight storage. Inventory all packed tensors and temporary
allocations before declaring any fit. Keep expert chunks within device binding
limits and avoid a whole-model unpacked host copy.

For f16 KV, the model-wide cache estimate is
`48 × 2 × 4 × 128 × 2 × context × conversations` bytes: **384 MiB at 4,096
positions and one conversation**, excluding padding, scratch and duplicate
buffers. Measure host RAM, browser memory and GPU peak separately, including
cold download/staging peaks. Preparation host disk/RAM requirements must come
from the selected artifact and conversion strategy, not the GPU weight budget.

## Prediction

Most arithmetic can reuse existing kernels. Routing semantics, geometry,
manifests and composition are the principal gaps. More workers increase
available memory but may worsen single-conversation latency through network
hops. No speed or capacity claim is established yet.

## Gate

Proposed acceptance criteria; freeze numerical tolerances, fixtures and the
performance regression threshold before running:

- Freshly compiled plans admit, serialize and reload with correct resource and
  state access. Unknown architecture, routing mode and unsupported quantization
  fail before allocation.
- Compare projections, per-head norms, router logits/IDs/weights, expert outputs,
  layer outputs and final logits against an independent same-quantization
  reference. Numeric tolerances are **TBD**. Test tied routing scores explicitly;
  document the reference tie policy instead of silently accepting different IDs.
- Require identical greedy tokens on the frozen fixture set across the accepted
  1/2/4-worker plans and relay/direct paths. Investigate any mismatch at its first
  divergent layer. Quantization quality versus the original checkpoint is a
  separate comparison, not a floating-point kernel tolerance.
- Frozen tool fixtures must produce the expected tool names and arguments,
  preserve streaming boundaries, and continue after deterministic mocked tool
  results. Test ordinary text and EOS as well. Fixture set: **TBD**.
- No OOM or state leakage across prefill, decode, chunk boundaries, reset,
  repeated turns and independent sequences. Record actual peak capacity.
- Existing families retain numerical behavior and optimization paths. Follow
  `CONTRIBUTING.md`: compile fresh affected plans, regenerate schema/browser
  outputs, type-check all families and run cross-family offline regressions.
  Record hardware parity and performance gates in
  `assets/TEST_OFFLINE_REFACTORING_VERIFICATION_BACKLOG.md`; fixtures alone do not
  establish equivalence. Preserve pooling, resident decode, grouped products
  and expert dispatch optimizations wherever applicable.

## Protocol and implementation order

1. Pin checkpoint/tokenizer/template revisions, quantized artifact SHA-256,
   tensor inventory and reference runtime. Confirm supported quant encodings.
2. Implement family admission and shared expert loading; compile one layer and
   inspect shapes/resources without executing a local workload.
3. Implement explicit softmax routing and the reusable tape composition; run
   layer and full-model numerical checks on an authorized inference host.
4. Prepare fresh 1/2/4-worker bundles; verify memory estimates, state isolation
   and tool fixtures before publishing or enabling catalog entries.
5. Measure cold load and warm TTFT, prefill tokens/s, decode ms/token and p50/p95,
   network time/bytes and memory. Use fixed 128/1,024-token inputs, 128-token
   outputs, chunk size 64 and at least five warm repetitions per arm. Record
   browser/backend, GPU, driver, cache/wire precision, RTT and bandwidth.
6. Compare relay and direct WebRTC with matching artifacts and prompts. A
   change in fleet size/hardware is a capacity comparison, not proof of kernel
   speedup. Separate GPU compute from transport and coordinator time.

No remote run or provisioning is authorized by this document. Host, rental
budget, teardown deadline, frozen tolerances and exact runnable commands remain
TBD. This workspace permits planning and offline checks, not numerical workload
execution. Keep the experiment open until the deciding measurements exist.
