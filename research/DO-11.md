## Question

Training nanochat's budget (about 4×10¹⁹ FLOPs) in a month needs about **15 TFLOP/s of useful compute**. The best pool today gives 51 GFLOP/s useful (experiment 61), from about 2.5 TFLOP/s announced by its 16 CPU workers: the raw compute is short by 6× even at full use.

Owners also compute in **float64** NumPy (`tf_owned_*` in `ygaraty/runtime/transformer_kernels.py`), which halves CPU throughput against float32.

**How much raw compute do float32 and GPU owners add, and how much of it reaches useful compute on home links, at today's batch and at larger batches?**

## Prediction, recorded before any code

- **Stage 0:** float32 owner kernels are 1.6–2× faster on CPU, and the update on home links only 1–4% shorter. Kernels are 6–10% of an update; the chain's latency dominates.
- **Stage 2 at 3,072 tokens:** GPU owners shorten the update by under 10%, for the same reason.
- **Stage 2 at 12,288 or 49,152 tokens:** the GPU pool's seconds per update grow much less than the CPU pool's. Useful GFLOP/s rises 4–15× over experiment 61.

**GPUs pay off only together with bigger updates (DO-10).**

## What has to be built

1. **Stage 0:**
   - `YGARATY_OWNER_DTYPE=float32|float64` (default float64) for owned-layer and vocabulary-slice state and kernels.
   - Parity: the loss stays within 5×10⁻⁴ of the float64 reference over 50 updates. That is the bf16-wire tolerance of experiment 34, now applied to arithmetic.
2. **Stage 1:**
   - A kernel backend `YGARATY_KERNEL_BACKEND=numpy|torch` for `tf_owned_layer`, `tf_owned_grad`, `tf_owned_step` and the vocabulary ops. It uses PyTorch on CUDA in float32: the same functions, re-expressed with `torch` tensors, with inputs and outputs still NumPy at the task boundary.
   - A benchmark script, `ygaraty experiment kernel_bench`, timing each op at bands of 8, 32 and 128 examples on CPU float64, CPU float32 and GPU float32.
   - A parity test against the float64 reference per op (relative error ≤ 1e-5).
3. **Pods:** GPU worker sizes in `ygaraty/experiments/pods.py`. The RunPod provider takes a GPU type, or DigitalOcean GPU Droplets if the account has them. Check with `ygaraty experiment pods price`.
4. **Placement:** GPU workers announce their GFLOP/s at hello, so capacity placement gives them the layers. Experiment 42's rule, one layer per fast worker, applies unchanged.

## Design

**Stage 0, workstation, 1.06M and 30.3M models.**
- Kernel benchmark, float64 against float32.
- Then experiment 59's 1.06M home-link setup, A (float64) against B (float32), 3 runs each.
- Gate: losses within tolerance; report the update change.

**Stage 1, one GPU machine, about 1 hour.**
- Kernel benchmark and parity tests for all three backends.
- Record the speedup per op and band size.

**Stage 2, mixed pool.**
- Coordinator g-8vcpu-32gb, 8 c-2 weak workers shaped to 100/20 Mb/s, 8 GPU owners shaped to 500/100 Mb/s, 50 ms round trip, handoffs on: experiment 61's link setup with the strong workers replaced.

| Arm | Owners | Tokens per batch |
|---|---|---|
| C3 | experiment 61's c-8 CPU (reuse its 4.64 s) | 3,072 |
| G3 | GPU | 3,072 |
| G12 | GPU | 12,288 |
| G48 | GPU | 49,152 (if memory allows) |

- 3 interleaved repeats, 22 updates each.
- Report seconds per update, useful GFLOP/s, and the KPI in years. The KPI uses learning per pair from DO-10 at each batch size; until it exists, use fixed-batch learning curves.

## Gate

- **Correctness:**
  - losses within 5×10⁻⁴ of the float64 reference over the run;
  - the same placement groups as experiment 61, GPUs taking the owned pieces.
- **Counts as a lever:** G12 or G48 at least **3×** the useful GFLOP/s of experiment 61's 51.3, beyond the spread.
- **Predictions:**
  - G3 within 10% of C3;
  - G12 at most 2× G3's seconds per update;
  - weak workers' unowned tasks become the pace if owners are fast. Watch the chain trace for it.

## Trigger

**Stage 0, workstation:**
```bash
git pull && pip install -e . && python -m unittest tests.test_owner_dtype
ygaraty experiment kernel_bench --backends numpy64 numpy32 --bands 8 32 128 --output runs/experiments/DO-11/bench-cpu
# then experiment 59's command with YGARATY_OWNER_DTYPE=float32 for arm B (see [experiment 72](072-split-backward.md)'s trigger for the full line)
```

**Stage 1, one GPU machine:**
```bash
ygaraty experiment pods up do7g --provider runpod --workers 1 --worker-size <gpu-size> --minutes 90 --max-hourly 2
ygaraty experiment pods ship do7g
ygaraty experiment pods ssh do7g w0 -- "cd ygaraty && pip install -e '.[torch]' && python -m unittest tests.test_torch_backend && \
  ygaraty experiment kernel_bench --backends numpy64 numpy32 torch --bands 8 32 128 --output runs/experiments/DO-11/bench-gpu"
ygaraty experiment pods fetch do7g && ygaraty experiment pods down do7g
```

**Stage 2, mixed pool:** experiment 61's Reproduce section, with the second `pods up` creating 8 GPU workers instead of c-8. On the GPU workers set `YGARATY_KERNEL_BACKEND=torch YGARATY_OWNER_DTYPE=float32`. Per arm set `YGARATY_BATCH_TOKENS`. Arm C3 is not rerun.

## Cost and limits

- **Cost:**
  - Stage 0 is free.
  - Stage 1 is about one GPU-hour.
  - Stage 2 is 8 GPU workers for about 2 hours. Price it with `pods price` first; a ceiling of about $25 is assumed here, and the run should not go ahead above it.
- **Limits:**
  - **Different parity rule:** float32 owners give up bit-identical losses against today's float64 owners. Parity is the reference tolerance, as for the bf16 wire.
  - **Data-center GPUs on emulated home links,** not volunteers' GPUs.
  - **Weak workers stay on CPU.** The unowned tasks may set the pace instead.
