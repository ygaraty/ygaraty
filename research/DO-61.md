## Question

In experiment 113 one contributor served Kolibri-1 at about 285 ms per token through production, against 125–174 ms with the coordinator on the same machine: each decode step seems to wait for a round trip to the coordinator. If a one-stage session keeps the loop on the contributor (the token it produced is its next input; the coordinator only receives the stream), does production decode fall to within a few ms of the on-machine time, with the same tokens?

## Prediction

Per token ≈ GPU step (≈140 ms on the A100) instead of step + RTT; about 2× faster on a transatlantic link; tokens bitwise identical (WS-27: the chat path is repeatable).

## Gate

### Part 1, workstation screen (frozen 2026-11-12, before running)

S5-nano Q4_K_M, one stage (`qwen35_session local --chat --splits 0,32 --capacity 4096 --generate 64 --record-turn-ids`), headless Chromium on the Radeon 680M, one session per run, three chat turns (`chat_cycles` prompts, cycle 0, turns 0–2, 500 words) over HTTP `/api/chat`, then a graceful end. Arms:

- **R**: `--loop relay --relay-delay 140`: every token back through the coordinator, held 140 ms (113's round trip through production was about 145 ms);
- **L**: `--loop local --relay-delay 140`: the contributor feeds its own token; the delay still holds whatever the coordinator sends it;
- **Z**: `--loop relay` with no delay: the on-machine reference.

Order R L Z L R Z Z L R (3 runs per arm). Per run: the median over its three turns of the coordinator's ms per token; per arm, the median over its runs.

- **Correctness:** every run's prompt ids and generated tokens (all three turns) identical to the first Z run's.
- **Works** if L's median ≤ 1.10 × Z's + 2 ms and ≤ 0.7 × R's, with correctness. Otherwise **Rejected** (a correctness break: **Failed gate**).

### Part 2, rented GPU through production (frozen 2026-11-14, before renting)

The production Qwen3-Coder-30B-A3B one-contributor session of DO-62 (relay route), after its loads,
contributor on the rented A100 with weights cached (warm rejoin, no `--cold`). Arms, by page switch:

- **L**: default (the contributor feeds its own token, resident loop as deployed);
- **R**: `--page-param loop=relay`: every token back through the coordinator.

Order L R R L L R; in each block one `chat_load --chats 1 --max-tokens 256` run (its first fixed prompt), driven from the workstation through `https://coordinator.example.org/v1`. The round trip to the
coordinator is measured from the machine (`curl` timing, 5 samples) alongside. Per block: the chat's ms per token
after the first; per arm: the median over its three blocks.

- **Correctness:** the generated text identical in all six blocks.
- **Works** if L's median ≤ 0.7 × R's, with correctness; L's median is also reported against the on-machine A100
  figure of DO-80 (24.3–24.8 ms per token, `local` harness, short context), descriptively.
- **Rejected** if L's median > 0.7 × R's; a correctness break: **Failed gate**.

(The earlier proposal's on-machine arm is replaced by DO-80's on-machine figure: no second coordinator on the machine.)
