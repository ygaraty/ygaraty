## Question

Can the existing Qwen3.5 backend run S5-nano text generation correctly without
Torch in contributors, and what memory and latency does distribution add?
Compare one browser with two contiguous 16-layer stages. Reuse the shared
loader, manifests, shaders, coordinator and verification harness rather than
creating a model-specific engine. Related: [92](092-qwen35-webgpu-four-contributors.md).

## Prediction

The shared attention geometry permits kernel reuse. Smaller hidden/FFN widths
reduce weight and projection costs, but attention/recurrent widths and cache
cost per token remain unchanged. Two contributors may be slower when one GPU
fits the model, because of activation transfer and relay latency.

## Gate

Proposed gates to freeze before running:

- Compare a linear and full-attention layer against a reference using the same
  dequantized GGUF bytes: finite outputs, elementwise atol=1e-3, rtol=1e-3.
  Check recurrent and KV states as well as hidden outputs.
- For fixed Portuguese/English prompts, compare chunked prefill and cached
  decode against the same-weight reference. Record logits and margins; require
  exact greedy agreement for 128 generated tokens on the frozen prompt suite.
  Token disagreement is a failed gate to investigate, not automatic permission
  to increase tolerances.
- One versus two stages must preserve those token sequences. Repeat with F32
  wire/cache diagnostically and F16 wire/cache as the deployment candidate.
- At 8,192 prompt tokens plus 128 generated tokens, complete without device loss
  or allocation failure. Record application allocations, driver/browser memory,
  cold load time, TTFT, median/p95 decode latency and bytes across boundaries.
  Latency is descriptive; no speedup is presumed.
- Re-run the existing Qwen3.5-9B fixture after the refactor to catch regressions.

## Protocol

1. On the authorized GPU host, pin revisions and hashes for the official
   [config](https://huggingface.co/maritaca-ai/S5-nano/blob/main/config.json),
   tokenizer/template and [Q4_K_M GGUF](https://huggingface.co/maritaca-ai/S5-nano-GGUF).
   Inspect all tensor types and converter ordering; do not infer them from the
   filename. Exclude vision and MTP from the initial execution graph.
2. Use the existing `qwen35_webgpu` layer/pipeline/contributor harness with the
   S5 config. Confirm tied output weights, normalization offsets, head ordering,
   partial RoPE and separate 2,560 hidden / 4,096 attention widths.
3. Freeze a short Portuguese/English prompt suite, token IDs and expected
   template rendering. Test one-token decode, nonaligned prefill chunks,
   reset and multi-turn history. Add Think/Instruct and retained reasoning
   history checks once the exact template is integrated. Greedy parity comes
   before stochastic sampling comparisons.
4. Run on one GPU, then two stages (0–15 and 16–31); record topology, GPU,
   browser/driver, context limit, chunk sizes and precision. Account for tied
   embedding weights being resident on both endpoint machines when split.
5. Save reports under `runs/experiments/DO-42/<host>-<timestamp>/`. Torch is
   permitted only in the separate reference environment. No runtime fallback.

## Limits

No S5 checkpoint was loaded or executed here. Configuration and mocked allocation
checks are not shader or numerical parity evidence. Vision, MTP and 262K context
are not initial support claims. Quantized parity does not reproduce BF16 quality.

### First external-host test

Implementation now includes a metadata-only `inspect` mode and rejects
unsupported tensor shapes/quantizations before creating a stage. Ten offline
contract tests pass. This is ready to attempt numerical testing, not an assertion
that the S5 checkpoint or shaders pass. The following paths are placeholders for
files already on the development host; nothing is downloaded by these commands.

```sh
python -m ygaraty.experiments.qwen35_webgpu inspect \
  --gguf /data/s5/S5-nano-Q4_K_M.gguf --config /data/s5/config.json \
  --out runs/experiments/DO-42/inspect

python -m ygaraty.experiments.qwen35_webgpu stage \
  --gguf /data/s5/S5-nano-Q4_K_M.gguf --config /data/s5/config.json \
  --tokenizer /data/s5/tokenizer.json --first 0 --last 4 --chunks 3,1 \
  --kv f32 --out runs/experiments/DO-42/first-four

python -m ygaraty.experiments.qwen35_webgpu pipeline \
  --gguf /data/s5/S5-nano-Q4_K_M.gguf --config /data/s5/config.json \
  --tokenizer /data/s5/tokenizer.json --splits 0,32 --generate 32 \
  --kv f32 --wire f32 --out runs/experiments/DO-42/one-browser
```

Run sequentially and inspect each report before advancing. `stage` covers three
linear layers and one full-attention layer, then a cached token. Pipeline compares
generated logits/tokens to the same-weight reference. These older numerical
harnesses report errors; process exit alone is not acceptance against the gates
above. Use fresh output directories on repeats. Reference stages require the
optional verification environment and sufficient CPU RAM for dequantized weights.

After passing, repeat pipeline with `--splits 0,16,32`, then with F16 KV/wire.
Both pipeline cases are still one browser: they test partition semantics, not
network latency. Finally use the existing `qwen35_session serve` path for two
physical contributors with the same config and split. Do not use `--chat` as
S5 chat acceptance yet: exact template/sampling integration is still pending.

### Shared-kernel extraction

Qwen/S5 and Phi-4 now import `webgpu_kernels.mjs` for common numerical primitives
and GPU resource/dispatch operations. Model topology and specialized attention
remain in the adapters. The remote harnesses serve the new module explicitly.
Twelve offline contract tests pass; extracted shader source matches the committed
pre-refactor implementation. Repeat both Qwen9B and S5 GPU fixtures after this
refactor; no real-system validation is implied by moving unchanged shader code.

### Typed model adapters

Qwen/S5 and Phi-4 adapters now build from strict TypeScript alongside the common
kernel runtime. Manifests, packed weights, stage inputs/results and Qwen layer
state are typed. Runtime manifest checks reject malformed network data; the
TypeScript declarations do not substitute for those checks. Thirteen offline
tests pass, including compile-time rejection fixtures. The existing HTTP URLs
and WGSL algorithms are unchanged. Repeat the remote numerical checks above
using the generated modules; contributor transport scripts remain JavaScript.
