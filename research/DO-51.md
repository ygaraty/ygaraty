## Question

Can the complete S5-nano model serve chat sessions on
one contributor with an 8 GiB GPU budget, and what changes in memory, token
parity and latency when the chat browser connects directly to that contributor?
There is no worker-to-worker transfer in either arm. Direct means a link between
the chat browser and the single contributor, not a self-link between stages.

Related: [DO-42](DO-42.md) covers model parity and one-versus-two-stage costs;
[DO-47](DO-47.md) covers compiler migration parity; [103](103-fast-sessions-rollout-rerun.md)
measured two-worker direct sessions; [DO-50](DO-50.md) covers repeated-turn
stalls and recovery. None establishes the single-worker direct endpoint path.

## Prediction

The quantized model may fit within an 8 GiB contribution at capacity 4096,
including caches and scratch. This is a hypothesis, not a measured allocation
or admission guarantee. Relay and direct should produce identical tokens with
the same weights, input and kernels. Direct may reduce prompt/token transport
latency; the gain may be much smaller than the two-worker result because no
hidden activations cross a worker boundary.

## Gate

Proposed criteria to approve and freeze before the first run:

1. **Memory/feasibility:** complete cold load, admission, prefill and decode on an
   actual 8 GiB GPU without allocation failure or device loss. Peak tracked GPU
   buffers must remain within 8 GiB, including weights, caches and scratch.
   Record driver/browser GPU memory, host RSS and transient loading peaks
   separately. A user-selected 8 GiB budget on a larger GPU is only preliminary
   evidence; it does not establish feasibility on an 8 GiB device. An 8 GiB
   unified-memory computer is a separate case because the OS/browser share RAM.
2. **Correctness:** both routes generate exactly the same greedy token sequence
   for every replayed input and conversation history. Compare captured finite
   logits bitwise on the same device and runtime; investigate any mismatch
   rather than accepting a near-tie exception. Establish repeatability with two
   relay runs first. Route parity does not replace DO-42's model-reference checks.
3. **Transport:** the direct data channel is open before prompt delivery, and
   its byte counters demonstrate prompt/token traffic. No contributor self-peer
   or duplicate first/last endpoint deliveries. Record candidate type and RTT;
   a TURN-relayed data channel is reported separately from peer-to-peer traffic.
   HTTP fallback is not counted as a successful direct measurement.
4. **Lifecycle:** complete three successive turns, cancellation followed by a
   fresh turn, and contributor replacement/reload on both routes. Intentionally
   break the direct link and verify fallback completes without duplicate or
   missing tokens, or reports an explicit failure within a predeclared timeout
   (proposed 30 s). No indefinite connected-but-stalled state.
5. **Latency:** report cold load, warm TTFT, median/p95 inter-token latency,
   tokens/s, setup time and transport bytes for every arm. Performance is
   descriptive: no speedup is required for correctness/feasibility to pass.

## Protocol

Use the existing pinned S5-nano Q4_K_M checkpoint and its own chat template;
record exact hashes rather than resolving a moving model revision. Fix f16
cache/wire, capacity 4096, chunk 64, one conversation and greedy decoding.
Disable speculative decoding and hold kernel policy constant between arms.

Freeze Portuguese and English prompt token arrays. Include a short prompt,
a 1024-token prompt, and a 3968-token prompt with up to 128 generated tokens;
never exceed capacity. Keep EOS behavior unchanged and retain early-stop cases
for correctness, excluding them from a timing cell requiring 32 decode tokens.
Run the three-turn and lifecycle checks separately from the long-prompt cases.

First run relay correctness and memory admission, then direct correctness and
lifecycle checks. For timing, warm both arms and perform five paired relay/direct
runs on the same GPU, alternating order. Reset conversation state between pairs
and retain identical warmed weights. Separate snapshot/logit capture runs from
timing runs so observation overhead does not contaminate latency.

The existing user-session harness may need single-worker endpoint support;
exact commands and artifact paths are TBD until that implementation is ready.
Save the source SHA, compiled plan/bundle, frozen gate, input/model hashes,
GPU/browser metadata, tokens/logits, peak allocations, raw timing samples,
transport counters and failures under
`runs/experiments/DO-51/<host>-<timestamp>/{relay,direct}/`.

## Implementation (2026-11-10, offline)

The second prerequisite (one-stage direct admission and signaling) is coded:

- `qwen35_contributor.mjs`: direct chat no longer depends on links between
  stages. A contributor that is both the first and the last stage opens only
  the chat link (`chatDirect`): prompts arrive over it (claimed with the
  coordinator's single-use permit, relayed after 2 s otherwise), and each token
  goes to the chat browser over it and to the coordinator, which relays it back
  to the same stage to run, exactly as in a relay session. The coordinator still
  applies the stop rule and never runs a turn's last token. No `Peers`, no
  stage-to-stage signaling and no 30 s link wait in a one-stage session.
- `prepared.py`: no longer refuses direct routes for one stage.


Offline checks: `tests/test_chat_direct.py::test_one_stage_is_both_chat_endpoints`
(signaling both ways, claim, a relayed token runs and the turn's last does not),
WebGPU suite 95/95.
A one-worker bundle of the tiny Kolibri test model (`ygaraty model prepare
--workers 1`) loads in `PreparedSession` on relay, webrtc and private routes,
with `plan_route` `{next: 0, output: token}` and `chat_direct` set. No browser,
WebRTC connection or GPU was used; the contributor page change is syntax-checked
only.

Not covered: the chat page (`session_chat.mjs`) already links to the distinct
set `{0, stages - 1}`, so it opens one link; this is read from the code, not
run. Byte counters for the chat link (gate 3) are not yet reported by the
contributor's route stats, which cover stage links only; the chat page's
`edges` would need to expose them, or the harness reads them from
`RTCPeerConnection.getStats()`.
