## Question

Can we remove PyTorch from the deployed Phi-4 inference workers while preserving
Ygaraty's Tape, compiler, placement, task protocol, persistent KV state and output
semantics? Measure deployment footprint, startup, memory and latency separately.

This explicitly tracks the runtime dependency, rather than assuming that faster
kernels eliminate it. Related: [DO-19 kernel optimization](088-phi4-owner-kernels.md),
[DO-18 distribution baseline](086-phi4-split-one-a100.md), [experiment 82](082-phi4-int4-vast-8gb.md).
PyTorch may remain an optional development/reference dependency; removing it from
training and all of Ygaraty is outside this experiment's scope.

## Shared numerical framework with WebGPU

User requirement (2026-11-05): develop this together with [DO-23](DO-23.md).
Ygaraty owns the numerical operation contracts for every operation required by
its inference graph. Native and browser workers implement the same contracts;
neither deployed inference backend requires PyTorch. PyTorch is an optional
independent test oracle, not an execution fallback.

Define shapes/layouts, storage and accumulation precision, quantization scales
and rounding, masking, absolute positions, buffer ownership, error behavior and
state transitions per operation. Version this contract and capability negotiation.
Cover embedding/gather, linear/matmul including packed quantized weights,
RMSNorm and reductions, RoPE, grouped-query causal attention and softmax,
SwiGLU/elementwise/residual operations, KV append/read/reset, final projection,
argmax and boundary conversion. Inventory the existing Tape operation set;
explicitly mark unsupported operations rather than silently delegating to torch.
Extend coverage systematically; the first completion gate covers the full Phi-4
inference graph, not every training operation in the repository.

Use shared golden fixtures and per-operation conformance checks across a CPU
reference, native GPU kernels and WGSL/WebGPU kernels, followed by block and
end-to-end parity. Precision-specific tolerances are explicit; FP16 is not BF16.
Allow backend-specific fusion, layouts and optimized numerical libraries behind
the contract. Owning the framework does not require rewriting every vendor
matrix kernel or forcing identical shader code across GPUs.

Acceptance additionally requires a complete native no-torch run and a complete
browser no-torch run, plus a mixed-owner pipeline exercising the same versioned
contracts. DO-23 can progress through its single-layer gate in parallel; full
cross-backend acceptance is shared, not a circular prerequisite. Measure native
runtime removal and browser portability separately from algorithm/kernel gains.

## Why specialization could make Ygaraty leaner

The user's prior fixed-model C decoder experience motivates this hypothesis;
it is not evidence of a Phi-4 speedup. A specialized executor can call the same
BLAS or GPU kernels as a general framework while doing less work around them.
The opportunity is to turn information already present in the Tape into an
execution schedule with explicit shapes, layouts, buffer lifetimes and state.

**Smaller deployment surface.** A worker needs only the operations and backend
required by its assigned stages. Removing the general tensor runtime may reduce
installed bytes, import/initialization time and resident host memory. Measure the
complete deployment, including the interpreter if retained, numerical libraries,
drivers, shaders and weight-loading buffers: a small C executable does not mean
its transitive dependencies or weights are small. No universal saving in seconds
or megabytes is assumed.

**Plan memory once, reuse it across tokens.** Liveness analysis can reuse scratch
buffers after their final consumer, retain views where layouts permit, and use
in-place operations only when aliases and retries allow them. Allocate KV storage
under a declared session budget instead of copying the full prefix on each token.
Keep quantized weights packed when the chosen kernel supports them. Reserve
space for transfer buffers and overlapping sessions as well as arithmetic.
This could admit a larger layer range on the same device and remove a network
boundary; that secondary benefit must be measured separately from kernel speed.

**Less work per decode step.** Validate static contracts when loading the plan,
then execute a prepared schedule with stable handles and minimal host dispatch.
Cache weight layouts and input-independent rotary tables where appropriate.
Input-dependent RMSNorm statistics cannot be folded into constant weights.
Retain dynamic checks for positions, bounds, session state and ownership changes.
CPU implementations can use a controlled persistent thread pool and coordinate
BLAS thread counts; GPU implementations need explicit command submission and
synchronization rather than an assumption that CPU threading solves launch costs.

**A consistent native/browser path.** The portable asset is the operation and
memory contract, not one C binary for every device. Native workers can lower it
to native GPU/CPU calls; browsers lower it to WGSL and WebGPU buffers/commands.
Both can consume versioned manifests, common fixtures and the same stage protocol.
This makes capability discovery, diagnostics and mixed-owner execution consistent
while preserving backend-specific optimization. A C implementation is not itself
a WebGPU implementation, and different precision/support limits remain explicit.

**Preserve generality in the compiler.** Rather than hand-maintain a complete
runtime per model, specialize a supported Tape graph into a small executor and
reuse the operation library across models. The initial scope is Phi-4; unsupported
operations must be rejected. New models, quantization formats and hardware still
require engineering and validation. Training/autograd support is a separate scope.

These advantages are not automatic. PyTorch can reuse cached allocations, use
views, disable autograd for inference, compile/fuse graphs and replay CUDA graphs.
It does not necessarily allocate fresh physical storage for every intermediate
or retain every layer's input. The fair baseline enables the relevant mechanisms.
Likewise, input chunking bounds temporary activation storage, but Phi-4's exact
full-attention KV cache grows with context and concurrent sessions. A bounded
context cap or paging policy makes memory controlled, not independent of input
length. Dropping history would change the model and is not a runtime optimization.

## Apples-to-apples attribution

Use two explicitly separated comparisons:

1. **Runtime-only:** same physical GPU/CPU, weights, quantization, accumulation
   precision, input/output tokens, batch sizes, cache policy, transport and
   numerical kernels where possible. Give both sides equivalent preallocation,
   warmup and inference settings. Compare dispatch, initialization, footprint and
   latency. If the kernel sequence differs, disclose it rather than calling the
   result pure runtime removal.
2. **Best backend:** optimized PyTorch versus optimized native/WebGPU execution,
   with the same task-quality target and resource constraints. Fused INT4 matmul,
   changed layouts or precision may improve this result, but are separate causes.

Record CPU thread counts, affinity, backend library versions, GPU clocks/power
settings and concurrent load. Measure cold process start separately from cold
weight loading and warm token generation. GPU timings must include completion,
not just enqueue time. Report active and reserved GPU memory separately, and
include total process memory and installation dependencies. Use paired repeated
runs and the same correctness fixtures; report uncertainty and losing cases.

Success may mean smaller workers with unchanged decode speed, lower startup cost,
or faster tokens. Each is useful, but they are distinct claims. It does not remove
WAN round-trip latency or establish cheaper requests without utilization and
end-to-end cost measurements.

## Prediction

A worker without PyTorch should be feasible using native numerical kernels and
an explicit buffer/cache implementation. It may reduce installation size, startup
and host-memory use. Decode speedup is uncertain: replacing full-matrix INT4
unpacking with a fused kernel is a distinct change and must not be attributed to
removing the framework.

## Gate

Proposed, not frozen:

1. Dependency removal: run in a clean worker environment without torch installed.
   Load local pinned weights, prefill, decode, emit tokens and release a session;
   exercise both one-owner and two-owner paths. No subprocess/service delegating
   computation back to PyTorch, no fallback torch import. Record transitive
   runtime dependencies and loaded libraries, not just direct Python imports.
2. Correctness: validate each block, final logits, chunked prefill and cached
   decode against the same weights and arithmetic reference. Freeze numerical
   tolerances and near-tie rules before execution. Preserve session isolation,
   position validation, retries, cancellation and output deduplication.
3. Report dependency removal separately from performance. Proposed performance
   acceptance: no more than 5% regression in median/p95 warm decode latency on
   matched hardware/workloads. An installation/startup improvement does not imply
   faster decoding. Absolute thresholds and repeat protocol require confirmation.

## Protocol

- Audit imports through checkpoint loading, owner dispatch, tensor allocation,
  kernels, synchronization and cache cleanup. Distinguish host Python overhead
  from PyTorch dispatcher overhead and device kernels.
- Define the minimum backend contract behind phi4_load/phi4_stage/phi4_end:
  immutable weight handles, device buffers, owned KV cache, synchronization and
  boundary tensor conversion. Keep Ygaraty's coordinator and transport.
- Select a native backend/kernel library after checking support for Phi-4's
  RoPE/GQA/SwiGLU and the exact quantized checkpoint format. Backend selection and
  supported hardware are TBD. Native CUDA libraries are allowed; they must be
  listed as dependencies. This does not require removing Python itself.
- Compare current PyTorch, optimized PyTorch (DO-19), and the native worker.
  Where possible share the same numerical kernels between optimized PyTorch and
  native execution to isolate runtime overhead. Otherwise label the comparison
  as an end-to-end backend change; do not claim a pure framework speedup.
- Use identical checkpoint hashes, quantization, prompt tokens, generated-token
  limits, precision, hardware and topology. Initial lengths: 128/1024/3968 prompt
  tokens and up to 128 generated tokens. Record EOS and actual lengths.
- Measure installed dependency bytes, process RSS, allocated/peak GPU memory,
  initialization excluding and including weight loading, TTFT, decode median/p95,
  throughput, CPU dispatch time and GPU execution. Use synchronized device timing
  and monotonic host clocks. Use at least five warm repeats and repeat borderline
  outcomes; do not infer request-tail statistics from too few sessions.
- Store source revision, exact commands, environment manifests, fixtures and raw
  measurements under runs/experiments/DO-30/<host>-<timestamp>/. Commit the driver
  and analysis; report measured and simulated evidence separately.

Execution belongs on the authorized dev/test server, not this simulation-only
machine. No workload, browser or service was launched by adding this plan. Rented
hardware budget, teardown deadline, exact commands and frozen gates are TBD.
