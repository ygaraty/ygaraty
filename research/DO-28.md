## Question

While decoding, a crossing carries one token's activations, about 20 KB at float32 for Phi-4's width of 5,120. That is latency-bound, and smaller payloads barely help. Prefill is different: a 3,968-token prompt sends about 81 MB across w0 → w1 on today's float32 wire, in 8 chunks of about 10.5 MB.

Experiment 82 measured 28.1 s to first token at 3,968 tokens (22.4 and 33.7 s in its two sessions), against 5.2 s at 1,024. The spread between sessions points at the network, but the spans were not split by phase, so the transfer's share is unknown.

BloomBee (arXiv 2604.21072) codes fp16 activations losslessly by splitting bytes into planes and entropy-coding each plane. That cut payloads to 46% of raw, against 69% for zstd and 71% for ZipNN. Two changes stack here:
- a **bf16 wire** halves the bytes, but is lossy against today's float32 wire;
- **byte-split coding** is lossless, on either wire.

**At 3,968 prompt tokens, how much shorter is time to first token with byte-split coding on the float32 wire, with a bf16 wire, and with both, and do the tokens stay the reference's?**

## Prediction

- **Stage 0 decomposition:** a chunk's crossing takes 1–4 s on these hosts, so the transfer is 30–60% of prefill. If it is under 20%, stop: this lever is small.
- **Float32 + byte-split (lossless):** payloads 70–80% of raw. Float32 activations code worse than fp16, because the low mantissa bytes are close to random. Time to first token 10–20% shorter, with tokens bit-identical to the float32-wire run.
- **bf16 wire:** payloads 50%; with byte-split about 30–35% of today's bytes. Time to first token 30–45% shorter.
- **Tokens on the bf16 wire:** equal to the reference up to near-ties, as in experiment 82.
- **Encode and decode** take under 100 ms per 10 MB chunk on one core with zstd level 1.

## Gate

TBD, to be frozen before any run. Proposed:
- **Stop rule after stage 0:** if the w0 → w1 transfer is under 20% of prefill time at 3,968 tokens, report the decomposition and stop.
- **Primary:** the bf16 + byte-split arm's median time to first token at 3,968 tokens at least **30%** below today's float32 wire, over 3 interleaved warm sessions.
- **Correctness:** the lossless arm's tokens bit-identical to the float32-wire run; the bf16 arms equal to experiment 80's reference except at near-ties (margin below 0.5).
- **Report also:**
  - bytes per chunk, coded and raw;
  - encode and decode ms per chunk;
  - the 1,024-token prompt;
  - inter-token latency, which should not change.

## Protocol

1. **Stage 0, decomposition (free, from a rerun of experiment 82's timing with spans per phase):** per prefill chunk, w0 compute, upload, relay residence, w1 download and compute. Add phase spans to `phi4_owner` if missing.
2. **Code:**
   - `--wire bf16` for the hidden states between stages (the head stays float32);
   - `--wire-coding none|bytesplit-zstd1`: split each value into byte planes (sign and exponent apart from the mantissa), zstd level 1 per plane, chunked so that coding streams;
   - a round-trip test that decode(encode(x)) == x bit for bit on random and captured activations.
3. **Offline check first:** code captured prefill activations from stage 0 and report the ratios, before any timed run. This step is the same analysis as [OFF-7](OFF-7.md), on inference activations.
4. **Arms:** F32 (today), F32 + byte-split, BF16, BF16 + byte-split. Prompts of 1,024 and 3,968 tokens, 3 interleaved warm sessions each, 32 new tokens.

## Cost and limits

- **Cost:** about $1–2 on Vast.ai, mostly checkpoint downloads, as in experiment 82. Confirm a budget and teardown deadline before provisioning.
- **Limits:**
  - One pair of hosts. Internet bandwidth between them varies by the hour, so the arms must be interleaved.
  - A lower time to first token also follows from fused 4-bit kernels (DO-19), which shrink the compute side.
