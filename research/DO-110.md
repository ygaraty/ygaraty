## Question

The session page and `GET /v1/status` report per worker a `route` and `links` (`peer`, `state`, `path` direct or TURN, `protocol`, `rtt_ms`). These rows were only unit-tested (`session_view.py`, `tests/webgpu/test_cli_improvements.py`): native Node contributors have no WebRTC. Do browser contributors on two different internet hosts open a WebRTC link live, and do the rows report it correctly?

## Gate (frozen 2026-11-25, before renting; budget $1, teardown 1.5 h)

Vast.ai containers map only TCP ports (22, 8000, 8101), so the TURN server cannot run there with UDP; coturn runs on a DigitalOcean Droplet with a public address, next to the coordinator (`--public-url http://DROPLET:8000`, `--route webrtc`, `--turn-host DROPLET`, `--turn-secret-file`, TLS port off). Worker A runs on one Vast host, worker B on another.

1. The session becomes ready with the 2 workers.
2. Both workers' `/v1/status` rows show a link to each other with `state` connected or open, a `path` (direct or TURN) and an `rtt_ms`.
3. A short chat answers correctly (e.g. "What is the capital of France?" → Paris).
4. Recorded, not gated: whether traffic went over WebRTC or fell back to the coordinator relay (the `route` field and coturn's allocation log), and which path (direct or TURN). If time allows, a second session with `--route turn` forces TURN.

Passes if 1–3 hold. A clean "WebRTC cannot work on Vast containers without X" with evidence is a `Found` result.
