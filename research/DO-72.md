## Question

Can a one-worker Vast.ai VM run the browser contributor over WireGuard or
Tailscale, enforce the intended network boundary, and stop serving safely when
the tunnel fails, without falling back to a public path?

This open experiment studies overlay isolation for WebGPU contributors. The
public chat interface may remain accessible; contributor-facing traffic must stay
on the overlay. The coordinator and GPU host operator remain trusted.

## Prediction

A full VM provides the network controls needed for a kernel-mode overlay and
firewall enforcement. Browser WebGPU compatibility and reliable failure handling
remain unverified. Merely installing an overlay does not force traffic through it.

## Gate

Proposed gates, to freeze with the final configuration before running:

- The selected GPU VM passes the contributor WebGPU probe, loads a small existing
  one-worker plan, reaches ready and completes 10 short chat turns.
- Packet captures and socket/routing inspection show that contributor signalling,
  model traffic and answers use the intended overlay addresses. Public probes
  cannot reach contributor-facing application endpoints or Chrome debugging.
- An unrelated overlay identity cannot access the protected endpoints. Document
  separately allowed bootstrap, DNS, overlay transport and model-download traffic;
  do not mistake encrypted overlay packets on the public NIC for a routing leak.
- In three repetitions each, disconnect the overlay interface and block its
  transport while a chat is active. No application traffic escapes over a public
  route, and new turns cannot be served until overlay connectivity is restored.
  The panel reports the failure within 30 seconds (proposed timeout).
- After restoration, readiness is checked again and a fresh turn succeeds without
  an automatic replay of the interrupted turn.
- Teardown deletes the rental, revokes its overlay identity and leaves no
  accessible protected endpoint or unaccounted-for instance.

Any public application fallback or unauthorized access fails the isolation gate,
regardless of whether chat still works. Report GPU execution, isolation, failure
handling and cleanup as separate outcomes.

## Protocol

1. Prepare an authorized remote execution host. This experiment must not launch
   workloads, contributors or network services on the offline simulation machine.
   Obtain an explicit spending budget and teardown deadline before provisioning.
2. Freeze the VM offer/template, GPU, OS, driver, Chrome version, application
   revision, model/plan identity and overlay choice. Require Secure Cloud if that
   is the intended product tier; record its designation separately from VM support.
3. Configure a one-worker session in Relay mode with public Direct/WebRTC fallback
   disabled. Give the contributor a unique overlay identity, restricted access to
   the coordinator, and no access to unrelated peers. Keep public administration
   restricted and Chrome debugging local.
4. Establish readiness only after the overlay and firewall checks pass. Record
   boot/setup time, readiness time and ordinary chat latency without claiming a
   speedup. No training or dataset download is needed for this study.
5. Run allowed and denied connection probes from authorized test hosts; capture
   application routes and public/overlay interfaces. Use synthetic prompts and
   redact credentials, invitation links and overlay enrollment secrets.
6. Inject both tunnel failures, observe active and new requests, restore the
   tunnel and verify recovery. Repeat each fault three times. Keep a teardown
   mechanism independent of the tunnel under test.
7. Delete the instance by recorded ID, revoke overlay membership and verify both
   provider inventory and network access. Store evidence locally under
   `runs/experiments/DO-72/<host>-<timestamp>/` on the authorized host.

## Limits

Success establishes a tested network boundary, not confidentiality from the
coordinator, provisioning service or GPU host. It does not validate sealed chat,
hardware attestation, multi-worker plans, Direct/WebRTC routes, other VM images,
or general model numerical correctness. Availability of a qualifying Vast VM
is a prerequisite, not an established result.
