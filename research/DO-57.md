## Question

The 8 full-attention layers' KV cache, 16 KiB per token per stage in fp16, is what limits context on a 4 GB contributor. Storing keys and values in int8 halves it; int4 with a scale per group of 32 or 64 values quarters it. The dequantization is a few operations per value read, and decode is bound by reading memory, so time per token should barely change, and at long context it may fall because fewer bytes are read.

**With the full-attention KV stored in int8 or in int4 (per-group scales), how much longer a context fits a 4 GB stage, how much quality is lost against fp16, and does time per token change?**

Lossy on purpose: tokens can differ from fp16. The result is quality against fp16.

## Prediction

- **int8 (per-head scale):** loss within +0.005 nats/token of fp16 at 32k–128k; needles unchanged; greedy tokens identical for most of the first 128 tokens on chat prompts.
- **int4, groups of 32:** within +0.02 nats/token; needles at long context a few points lower. Keys are more sensitive than values: int8 keys with int4 values is a likely sweet spot.
- **Context on a 4 GB stage:** about 2× (int8) and 3.5× (int4, with scales) the fp16 limit, about 120k and 200k tokens.
- **Time per token** at 64k: equal or 5–15% lower than fp16.

## Protocol

1. **Code:** `--kv-dtype fp16|int8|int4 --kv-group 32|64`, keys and values separately settable; quantize on append, dequantize inside the attention kernel (no full dequantized copy).
2. **Arms:** fp16; int8; int4 g32; int4 g64; int8 keys with int4 values. All uncapped; then the best one combined with DO-56's best window.
3. **Final memory check:** experiment 97's two RTX 3060 contributors, the best arm, growing one conversation until the stage's peak memory reaches 4.0 GB.
4. **Prepare on the workstation:** round-trip tests of the quantizer against a NumPy reference (`tests.test_qwen35_kv_quant`); one S5-nano long-document loss run.
