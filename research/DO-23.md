## Question

Test real-layer parity and latency, then a mixed browser/Python pipeline, then a browser-only pipeline if capacity permits. Related to experiments 45, 48 and 81; these do not establish Phi-4 browser support.

Related: [Phi-4 GPU baseline](081-phi4-two-h100-pipeline.md),
[inference plan](../../inference.md).

## Shared numerical contract

Develop in parallel with [DO-30](DO-30.md): the WebGPU worker is a backend of
Ygaraty's own numerical framework, with the same operation semantics, checkpoint
layout/quantization contract, state transitions and conformance fixtures as the
native no-PyTorch worker. Implement WGSL kernels and GPU-resident buffers behind
that contract. No torch service or fallback may execute browser-assigned work.
The first layer gate can run independently; the final gate includes all Phi-4
operations and native/browser mixed-pipeline parity. Keep precision differences
explicit and reject unsupported capabilities before admitting a session.

## Prediction

A small browser-owned stage may broaden capacity, but slower kernels and added boundaries may hurt interactive latency.

## Protocol

Begin with a middle layer, FP32 fixtures then independently validated FP16. Query shader-f16 and buffer-binding limits; partition matrices locally when needed. Keep weights/KV resident and avoid per-operation JS readback. Compare native and browser execution on the same GPU where possible. Integrate one or two browser-owned layers with Python owners; keep final head on Python initially. Measure cold upload/compile separately from warm compute, readback, handoff and end-to-end time. Q4 is a later validated arm. Multiple tabs on one GPU are protocol checks, not machine scaling. Run browsers only on the authorized dev/test host.

All deciding runs take place on the authorized dev server or remote test machines,
not this simulation-only workstation. This entry authorizes planning only, not
provisioning. Host inventory, budget (if rented), teardown deadline, checkpoint
hashes and exact runner commands are TBD. No services or workloads were started.

Use pinned prompts of 128/1024/3968 tokens and up to 128 generated tokens for
single-session comparisons unless the frozen protocol explicitly changes them.
Record EOS and actual lengths. Start with at least five warm measured repeats,
report variability and repeat borderline outcomes; do not treat a handful of
session summaries as a reliable request-tail estimate for load tests. Use
monotonic clocks, synchronized GPU timing where needed and explicit timing
boundaries. Save commands, source revision, input hashes and raw traces under
`runs/experiments/DO-23/<host>-<timestamp>/`. Commit the driver and analysis code.
