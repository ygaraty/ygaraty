## Question

DO-108 ran the 27B as one worker on one GPU (4,096-token answer at 11.6 tok/s). With two workers on two hosts, every token crosses the internet twice through the coordinator's relay. Does a 4,096-token answer still finish correctly, at what speed, and does the speed hold as the answer grows?

## Gate (frozen 2026-11-25, before renting; budget $1, teardown 1.5 h)

1. The session becomes ready with worker A on host 1 and worker B on host 2.
2. "Count from 1000 to 3000 …" (DO-108's client) gives exactly 4,096 generated tokens with `finish_reason: length`, and every complete number is correct.
3. No failed request; decode speed in the last 256 tokens at least 0.8× the first 256.

Passes if all three hold. Speed per token and the hosts' round trip are recorded, not gated.

## Log

- 2026-11-25: `do109` (Vast.ai: server RTX 3090 Norway $0.232/h, w0 RTX 3090 France $0.258/h; w0 is 80.15.7.37, the host that report 181 suspected of being slow). `serve` refuses a plain-HTTP public URL for remote contributors and a public Cloudflare tunnel was not permitted, so worker B reaches the coordinator through an SSH local forward (B → A, a second sshd on A's mapped port 8101 that accepts only a throwaway key); both workers use the `http://127.0.0.1:8000` link. /health through the forward 0.12–0.20 s. Both workers' `/v1/status` rows showed downloading percentages and "coordinator connected" live.
- 2026-11-25: Ready after both downloads; long answer passed the gate at 3.6 tok/s. Logs fetched (keys removed); both machines deleted by recorded IDs. Cost about $0.35.

## Limits

The SSH forward is not how users connect: `launch --public` uses an HTTPS tunnel, a LAN uses HTTPS directly, so the per-token cost here mixes the relay with the forward's overhead and is an upper bound. Worker B's host (80.15.7.37) is the one report 181 suspected of being slow (24.5 of 128 CPUs allowed). The split between network time and compute per token was not measured; DO-110 showed WebRTC links between hosts work (72 ms round trip), which would avoid the relay's extra hops.
