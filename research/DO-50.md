## Question

Does repeated conversation state reuse, reset, or direct prompt delivery cause token stalls or permanently disabled chat controls? Can longer generations and repeated cycles expose failures missed by single-message smoke tests?

Related: [97](097-qwen35-webrtc-direct-links.md), [99](099-user-sessions-webrtc-close-stages.md), [103](103-fast-sessions-rollout-rerun.md). Those do not establish reliability of the new browser-to-endpoint chat flow. The observed production stall is a motivation, not an established root cause.

## Prediction

Repeated turns and resets may expose stale epoch/sequence/grant state. A connected data channel alone does not demonstrate prompt receipt, GPU progress, or token delivery. UI stream cleanup may independently keep Send disabled after the server reports an error. Separate transport, generation, and UI completion evidence is needed.

## Gate

Freeze this protocol and deployed revisions before execution. Proposed acceptance:

- Each no-fault arm: 3 repeats × 10 conversations × 10 turns; zero unexplained errors, missing terminal events, or locked controls. Report actual generated tokens; a requested cap is not a minimum output length.
- Session caps 256, 512 and 1024, subject to validated model context and memory limits. Do not silently raise production limits. Each cap is a separate dedicated-session run. Short EOS outputs do not validate the long-output condition: label it untested unless at least 10 turns per repeat generate 80% of that cap.
- After a terminal error, controls unlock within 2 seconds. With no HTTP progress, the new browser deadline is 130 seconds; controls must unlock by 135 seconds. The driver stops a blocked turn at 150 seconds.
- For subsequent runs after the 2026-11-10 timeout update, allow 30 seconds for peer connection and 35 seconds overall setup before explicit fallback (earlier runs used 10/15 seconds). The direct no-fault arm requires actual direct setup; fallback cannot be reported as direct success.
- Fault arms: bounded failure is acceptable; no duplicate prompt delivery, mixed epochs, or silent replay. After restoring connectivity, a separately recorded manual retry or New chat must complete. Never erase the initial failure by rerunning it in place.
- Compare baseline revision and candidate fix with identical bundle/plan/browser/hardware and alternating order. Report stalls per attempted turn and first-visible/whole-turn timings, not only successful-run latency. Exact token equality requires a separately controlled greedy run and matching histories; output hashes alone are not a correctness proof.

2. Keep ticket URLs, API credentials, signed downloads, SDP and IPs out of shared logs.
3. Start with Phi-4/two workers at 256 tokens. Preserve a baseline run before applying the UI recovery fix, then candidate. Expand caps, then S5-nano and Qwen using validated plans. No silent model/plan substitutions.
4. Run the actual chat page: HTTP-chat arm (do not click Enable direct chat), then direct-chat arm (require both endpoint links). The contributors' ring mode is held constant, independently of chat transport. Fresh chat context per arm; reset between conversations, retain history within each conversation.
5. Driver uses synthetic prompts with a cycle marker, follow-ups referring to prior context, and longer requested answers. Run 10 × 10 initially, then `--cycles 30 --turns 20` for a soak. Use a 2-hour external wall-clock watchdog; incomplete runs remain incomplete. Context-capacity resets must be logged and analyzed, not treated as uninterrupted long context.
6. Fault matrix, separate runs: (a) chat HTTP offline for 10 seconds on turn 2 using driver; (b) endpoint WebRTC link loss while signaling/HTTP stay available; (c) stage B disconnect/replacement; (d) chat page reload; (e) second chat tab competing for the direct lease; (f) coordinator restart on the isolated deployment. Only (a) is automated by this runner. Browser offline emulation does **not** establish UDP/TURN failure coverage. Run (b–f) with a remote operator, aligned event timestamps, no global production firewall changes.
7. For OpenAI compatibility, repeat the synthetic conversation sequence through `/v1/chat/completions`, `stream=true`, temperature 0, matching model and session ID, supplying full accumulated history; use a different dedicated session. Require `[DONE]`, bounded errors and actual usage/output counts. This is a control protocol, not implemented by the browser driver and not evidence of direct chat.
8. Capture coordinator turn start/end, timeout/reset/epoch, prompt grant/claim/fallback, first-stage prompt admission, last-stage generated token/sequence, and browser received token/terminal timestamps. Capture selected ICE candidate type and bytes/RTT deltas at chat and contributor endpoints. Existing stage `connected` snapshots are insufficient to classify chat as direct versus TURN. Missing telemetry must be marked unknown, not inferred. Instrumentation for these internal spans is a prerequisite for attributing a reproduced stall, not for detecting one.

## Reproduce (remote host only)

The checked-in driver is `scripts/experiments/chat_cycles.py`. It opens a chat page and sends real prompts; it does not provision contributors, change caps, download weights, or start a coordinator. Use a dedicated session that is already ready. Install Python Playwright/Chromium on the authorized Linux driver host using your pinned environment; record versions. The driver requires Linux plus explicit `--execute-remote`.

```bash
# Remote host, repository root. Paste the dedicated chat URL with #key=... privately.
read -rs -p 'Dedicated chat URL: ' YGARATY_CHAT_URL
export YGARATY_CHAT_URL
# Set this to the actual deployed source revision, not merely the driver's checkout.
export DEPLOYED_REVISION=YOUR_DEPLOYED_REVISION
mkdir -p runs/experiments/DO-50
# GNU timeout bounds the entire run, including browser startup/cleanup.
timeout --signal=TERM --kill-after=15s 2h python scripts/experiments/chat_cycles.py \
  --execute-remote --revision "$DEPLOYED_REVISION" --token-cap 256 \
  --arm relay --cycles 10 --turns 10 --words 500 \
  --out runs/experiments/DO-50/phi4-http-r1
# Run separately with a fresh context, same dedicated setup:
timeout --signal=TERM --kill-after=15s 2h python scripts/experiments/chat_cycles.py \
  --execute-remote --revision "$DEPLOYED_REVISION" --token-cap 256 \
  --arm direct --cycles 10 --turns 10 --words 500 \
  --out runs/experiments/DO-50/phi4-direct-r1
# Separate fault run: add --fault-turn 2, with a new output directory.
unset YGARATY_CHAT_URL
```

`--token-cap` records the cap; it does not change the session configuration. Configure and verify it before each arm. `--words` changes the prompt's requested length, not a token guarantee. `--timeout` bounds each turn/reset (default 150s). Output directories must be new, preventing overwrite. Nonzero exit means incomplete/failing; a killed run may have only incremental `events.jsonl`. Preserve those artifacts.

Artifacts: incremental `events.jsonl` (manifest, cycle/turn, reset, timing, generated tokens, output hash, generic browser/network failures) and `summary.json`. No raw chat URLs or credentials are recorded. Store external coordinator/contributor traces alongside them with secrets redacted. Driver first-visible timing is sampled at 200ms and excludes click overhead; generated counts come from terminal server events. Response collection waits for HTTP stream termination, deliberately flagging streams that fail to close.

## Limits

A clean soak reduces observed failure frequency; it does not prove absence of races. The runner alone does not identify a token stall's cause, exercise UDP faults, validate numerical correctness, or measure GPU memory. Browser request failures may include background polling. Existing debug telemetry does not fully expose direct-chat claims and token paths; retain unknowns until instrumented. API control and operator fault arms require the documented additional work before claiming the complete matrix passed.
