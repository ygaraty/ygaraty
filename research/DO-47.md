## Question

Does compiling the inference sequence to Tape tasks, then executing those tasks
and their distribution routes, preserve exactly what the previous release ran?
Check numerical outputs, persistent state, memory and latency. This tests an
execution-path change, not new kernels, quantization or model quality.

Related: [DO-42](DO-42.md) (S5), [101](101-twil-8b-dense-webgpu-family.md)
(TwIL), [102](102-three-four-worker-plans.md) (partitions), and the
[compiled-plan contract](../../docs/public/webgpu-library.md#compiled-inference-distribution-plans).

## Prediction

On the same GPU/browser with identical packed weights and input tokens, both
arms issue the same primitive kernel calls in the same order. The candidate
expresses layer/head compositions and per-sequence loops explicitly on Tape,
including weight/state bindings, scalar arguments and buffer offsets. Outputs and
application GPU allocations should be identical. Plan interpretation adds a
small CPU dispatch cost but should not materially change serving latency.

## Gate

Fix these criteria before starting. Score each model and partition separately;
do not hide one failure behind aggregate averages.

1. **Numerical identity:** every generated token matches, and all captured finite
   float32 logits, stage outputs and persistent-state snapshots are bitwise equal
   between arms at the same input/position. No near-tie exception: identical
   kernels are the premise. Reject NaN/Inf. Run the baseline twice first; if it
   is not repeatable, mark the exactness comparison inconclusive and investigate,
   rather than relaxing the gate after seeing candidate results.
2. **Execution/state:** task dispatch traces, submission layer counts and cache
   positions match. Chunked prefill, single-token decode, reset, reused slots,
   interleaved conversations and batched decode produce the same results.
   Invalid plans fail before execution. Cancellation and contributor replacement
   retain the baseline's replay/output behavior.
3. **Memory:** peak application-tracked GPU allocation is identical in paired
   cases and below the approved plan budget. Record browser/driver and host RSS
   separately; those noisy measurements do not substitute for allocation counts.
4. **Latency:** for each timing cell, candidate/baseline ratios of the medians
   across five paired runs are at most 1.05 for warm TTFT and median inter-token
   latency, and at most 1.10 for per-run p95 inter-token latency. Report every
   pair, including failures. If baseline variability exceeds these bands, report
   timing as inconclusive rather than passing it from a pooled result.
5. **Deployment compatibility:** both freshly prepared bundles and existing
   bundles without stored plans work. The latter receive plans at load time;
   weight hashes and download sizes remain unchanged. Relay and direct handoffs
   follow the compiled routes. A direct arm that falls back to relay is not a
   successful direct measurement.

Overall pass requires all applicable gates. A failure or an incomplete cell is
reported explicitly. Offline trace equality does not satisfy gate 1.

## Protocol

**Arms.** A is `32d65288d624867abe4d834b8c4f83e7860151ac`, before the compiled-plan
change. B is the committed candidate containing `inference/distribution.py` and
`inference_plan.mjs`; its SHA is **TBD before execution**. Use separate checkouts,
matching server/assets per arm and fresh sessions. Record any instrumentation
patch against both SHAs; only observation code may differ from the tested release.
Do not point both arms at a live production catalog or overwrite production data.

**Inputs.** Reuse the pinned Q4_K_M checkpoints, config/tokenizer/chat format and
hashes in `deploy/models/{qwen3.5-9b,twil-8b}.json` and DO-42's pinned S5 artifacts.
Record full SHA-256 values in the run manifest. No BF16 reference substitutes for
same-weight A/B comparison. Freeze token-ID inputs once per model, then replay
identical IDs in both arms; keep the model's own chat template unchanged.

| Model | Layer boundaries for 2 / 3 / 4 contributors |
|---|---|
| S5-nano | `0,16,32` / `0,9,23,32` / `0,6,16,26,32` |
| Qwen3.5-9B | `0,17,32` / `0,10,24,32` / `0,6,17,28,32` |
| TwIL-8B | `0,20,40` / `0,13,28,40` / `0,9,20,31,40` |

Use f16 cache/wire, chunk 64, capacity 4096 and a maximum 128 generated tokens.
Use greedy decoding with no sampling. Stop at EOS as normal; exclude runs with
fewer than 32 decoded tokens from timing, while retaining them for correctness.
Choose a frozen non-early-stopping timing prompt before candidate timing.

**Fixtures.** Include these short chat requests, then fixed 1024- and 3968-token
prefills produced by repeating a recorded text and slicing token IDs. Store the
exact arrays and their hashes; use the same inputs for every repeated run.

- `Write a Python function that returns the n-th Fibonacci number.`
- `Explique em português por que o céu parece azul.`
- `What is 17 times 23? Show the calculation.`

Run full-model correctness for all nine model/partition combinations on the
same dev-server GPU with isolated browser contexts. Then run each combination
with separate contributor machines, sequentially, on relay and direct routes.
Record actual GPU/driver/Chrome versions, hosts, stage assignments and routes.
If available hardware cannot cover a cell, leave it pending. Local loopback
measurements cannot stand in for cross-machine latency.

State coverage includes a short prompt split as `9,1,1,1`, decode to 32 tokens,
reset/replay, and two slots with different positions. Exercise `runBatch` at the
stage/harness level; the user-panel serving path remains one conversation.
Capture attention KV state and, for Qwen-family linear layers, recurrent and
convolution state. Keep full snapshots in correctness runs only.

For timing, warm the pipeline once per arm and perform five matched A/B pairs,
alternating AB and BA order with the same physical assignment. Disable full
logit/state dumps and tracing in both timed arms. Measure cold download/load,
compilation, prefill and warm TTFT separately; report median/p95 decode latency,
per-session tokens/s and application peak allocation. Do not mix warm execution
with checkpoint download time or infer GPU timings from simulations.

**Prerequisites still to record:** candidate SHA, exact dev-server/GPU/browser
inventory, input-token hashes, and instrumentation patch for per-step state and
batch captures. Existing pipeline checks emit `logits<i>.f32`; the full state and
cross-arm gate evaluator are not yet a dedicated runnable harness. Finish and
freeze that observation code before collecting results. If renting additional
hosts, obtain a budget and teardown deadline before provisioning.
